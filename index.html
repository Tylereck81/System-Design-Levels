What happens when someone opens your site

DNS · RFC 1034, 1035 · HTTP · RFC 9110

Start simple: one server runs everything, including the web app, the database and the cache. Follow one request:

  1. The user goes to api.example.com. The browser or app asks DNS where that is. DNS is usually a paid third-party service, not hosted on your servers.
  2. DNS returns an IP address, for example 203.0.113.42.
  3. The device sends HTTP requests directly to that IP: your web server. DNS is not on this path; it only answered the question.
  4. The web server returns an HTML page or a JSON response for rendering.

Devices keep the DNS answer for a while, so the lookup does not repeat on every request.

Two kinds of clients

HTTP APIs · JSON · RFC 8259

  • Browser: your server code (in Go, Python, Java…) does the work and returns HTML. JavaScript in the page draws it and handles clicks.
  • Mobile app: already has its screens built in, so it only asks for data. The server answers with JSON: plain text, easy to read in any language.

Front end, back end, web server. The front end runs on the user's device: HTML and JavaScript in the browser, or the mobile app. The back end is your code running on servers. This game calls that machine the web server; you will also hear app server or API server. In this game they are the same box.

Split the web tier from the data tier

Two-tier architecture

With more users, your code and your data start fighting over the same CPU and memory. Give each its own machine: web servers answer requests (the web tier) and a database server keeps the data (the data tier). Now each tier can scale independently: upgrade the database and leave the web server alone, or the reverse.

Which database?

Choosing a database · PostgreSQL, Redis, MongoDB, Cassandra, Neo4j docs

AspectRelational (SQL, RDBMS)Non-relational (NoSQL)
ExamplesPostgreSQL, MySQL, SQL ServerRedis (key-value), MongoDB (document), Cassandra (wide-column), Neo4j (graph)
Data modelTables with a fixed schemaFour families: key-value, document, wide-column and graph
JoinsYes, across tables in one queryUsually not: the app fetches each piece itself

Start with relational. Joins, transactions and decades of tooling cover most apps, and one well-tuned server goes a long way. NoSQL earns its place when:

  • you look items up by key and need a few milliseconds or less, at very high request rates;
  • records have no fixed shape, or there are few links between them;
  • you always read and write a whole object at once, such as a user's settings;
  • the data grows past what one relational setup can hold, and you need to spread it across many machines.

Scale up or scale out

Scaling up vs scaling out

A server at its limit makes every user wait, then starts refusing connections. You have two ways out.

  • Vertical scaling (scale up): move to a machine with more CPU and RAM. Nothing in your design changes, which makes it the right first move while traffic is small.
  • Horizontal scaling (scale out): add more servers to a pool. This is Level 2.

Scaling up runs into two problems:

  1. A ceiling. The biggest machine you can rent is still one machine, and the largest sizes cost the most per unit of capacity.
  2. No failover. One server is one point of failure. When it stops, the whole site stops.

Why a busy server gets slow

How this game simulates load · standard queueing result (M/M/1)

Each server in the game has a capacity in requests per second. Its utilization is ρ = load ÷ capacity. Requests wait in line behind each other, so the time per request is base time ÷ (1 − ρ). Above 100%, the extra requests fail.

The lesson for interviews: a system gets slow well before it falls over. Keep important servers comfortably below full.

Game assumptions: web server work 20 ms, database query 10 ms (about one disk seek), internet round trip 40 ms, round trip inside the data center 0.5 ms, DNS $5/month. A single server running both code and data handles half its capacity, because every request needs both. A NoSQL database cannot join, so a request that needs a user, an order and its products costs 3 lookups (3 ms each) instead of one SQL query.

Numbers to carry into the interview

A disk seek takes as long as 100,000 memory reads, so keep hot data in memory. Crossing an ocean costs more than ten disk seeks, so keep users close to their data.

Estimating QPS. Queries per second = daily active users × requests per user per day ÷ 86,400 seconds. Peak is about 2 × the average. Example: a photo app with 40 million daily users, each loading 30 pages a day: 40M × 30 ÷ 86,400 ≈ 13,900 QPS, peak ≈ 28,000.

Round hard: for a first guess, call a day 100,000 seconds (the answer comes out about 14% low). Say each assumption out loud, and put a unit on every number: "36 TB", never just "36".

Availability. 99.9% sounds high but allows 1.44 minutes of downtime a day, or 8.77 hours a year. Each extra nine cuts the allowed downtime by 10×: 99.99% is 52.6 minutes a year.
